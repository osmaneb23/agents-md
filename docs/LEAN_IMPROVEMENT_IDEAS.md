# Lean improvement ideas for agents-md

This is a product and engineering memo for making `agents-md` better without turning it into a bloated agent framework.

The core rule: every improvement should make generated `AGENTS.md` files shorter, safer, easier to trust, or easier to measure. If an idea only makes the tool look bigger, it should not ship.

## Current verdict

`agents-md` is useful because it targets a real failure mode: context files can hurt agents when they repeat generic project information or add unnecessary requirements. The project has a coherent thesis:

- read existing docs first
- keep generated output short
- include exact commands and boundaries
- update managed sections without deleting human notes
- score files for practical quality signals

The project is not yet proven in the stronger sense. It has no independent benchmark, no mature download history, and no user corpus. That is fine for v0.1, but it means the next work should focus on evidence and trust, not breadth.

## Evidence that should guide the roadmap

### 1. Context files can hurt

The ETH Zurich AGENTS.md study found that repository context files often reduce task success compared with no context and increase inference cost by more than 20%. The same abstract says unnecessary requirements make tasks harder and that human-written context files should describe only minimal requirements.

Product implication: the best version of `agents-md` is not "the generator that finds everything." It is "the generator that knows what not to write."

Source: https://arxiv.org/abs/2602.11988

### 2. Good AGENTS.md files are specific

GitHub analyzed more than 2,500 `agents.md` files and found successful ones use exact commands, flags, clear boundaries, stack specifics, and concrete examples. Vague helper-style prompts perform badly.

Product implication: static extraction should prioritize exact executable facts and repo-specific constraints over architecture summaries.

Source: https://github.blog/ai-and-ml/github-copilot/how-to-write-a-great-agents-md-lessons-from-over-2500-repositories/

### 3. Codex loads instructions as layered prompt context

OpenAI's Codex docs say Codex loads global and project instructions in a chain, walks from repo root to current directory, and stops once the combined project-doc size hits `project_doc_max_bytes`, which defaults to 32 KiB.

Product implication: `agents-md` should stay byte-conscious and eventually understand path-scoped instructions. Large generated files are not neutral; they consume prompt budget.

Source: https://developers.openai.com/codex/guides/agents-md

### 4. The open AGENTS.md format is simple

The public AGENTS.md format positions the file as a README for agents: a predictable place for context and instructions.

Product implication: do not invent a private framework unless the plain file cannot solve the problem. The format's strength is simplicity.

Source: https://github.com/agentsmd/agents.md

### 5. Adjacent tools are moving toward heavier systems

Several adjacent projects now package memory directories, MCP sync, multiple generated agent formats, tiered context, sub-agents, or eval loops. Some of that is useful, but it is also where bloat starts.

Product implication: `agents-md` can win by staying small and evidence-driven: one focused CLI, no runtime dependencies, no memory framework, no mandatory LLM.

Examples researched:

- `agentmd-gen` on PyPI advertises multi-format generation and an `eval` loop.
- `agents.ge` advertises `.agents/` memory and cross-agent synchronization.
- `.agents Protocol` proposes a full directory convention for skills, agents, models, tasks, and memories.

## Product north star

`agents-md` should answer one question better than any other tool:

> What is the smallest AGENTS.md that would actually prevent agent mistakes in this repo?

Everything else is secondary.

Good metrics:

- generated line count
- generated byte count
- number of exact runnable commands
- number of repo-specific conventions
- number of generic lines
- number of facts removed because they already exist in README/docs
- stale-input detection accuracy
- human edit preservation
- false-positive rate for conventions

Bad metrics:

- number of supported tools
- number of generated sections
- number of providers
- AGENTS.md length
- "AI-readiness" vibes
- architectural summary completeness

## Immediate fix-soon items

These are not big features. They are small trust and correctness improvements.

### 1. Pin the reusable GitHub Action's installed package version

Current state:

- README recommends `uses: osmaneb23/agents-md/.github/actions/agents-md-lint@v0.1.1`.
- The composite action runs `python -m pip install agent-context-md`.
- That means a user pinning the action to `v0.1.1` still gets the newest PyPI package at runtime.

Why this matters:

Pinned GitHub Actions are expected to be reproducible. Installing latest from PyPI breaks that expectation. A future package release could change lint behavior for old pinned workflows.

Lean fix:

- Add an action input named `version`.
- Default it to the package version that matches the action tag.
- Install `agent-context-md==${{ inputs.version }}`.
- In each release commit, update the default version.

Acceptance test:

- `action.yml` contains `default: "0.1.2"` for release `v0.1.2`.
- The install command includes `agent-context-md==${{ inputs.version }}`.

Do not build:

- Do not add a custom installer script.
- Do not vendor the package into the action.
- Do not make the action build from source again unless PyPI availability becomes unreliable.

### 2. Fingerprint all inputs that affect generated output

Current state:

- Fingerprints include key manifests and workflow files.
- Generated output also depends on README/docs facts, `.env.example`, some source files, test paths, and config files used by convention detection.
- If those change, `agents-md diff` may say nothing relevant changed even though an update would produce different output.

Why this matters:

`agents-md diff` is a trust feature. If it misses input drift, users learn not to trust it.

Lean fix:

- Keep the fingerprint compact.
- Add hashes for docs read by deduplication: root Markdown files except AGENTS output and symlink aliases, plus `docs/**/*.md`.
- Add hashes for high-signal config files already used by scanners: `.env.example`, `.env.sample`, `example.env`, `tsconfig.json`, `package.json`, `pyproject.toml`, lockfiles, task files.
- For source-derived conventions, do not hash every source file by default. Instead, add a deterministic "convention scan summary" with file count, first N matched relative paths, and maybe a hash of those paths plus snippets that triggered a convention.

Acceptance test:

- Changing README content that duplicates a generated command makes `agents-md diff` report a change.
- Changing `.env.example` makes `agents-md diff` report a change.
- Changing an unrelated source file that does not affect conventions does not flood the fingerprint.

Do not build:

- Do not hash the whole repository.
- Do not store long source snippets in the fingerprint.
- Do not make `diff` slow on large repos.

### 3. Prevent LLM synthesis from rewriting manual notes during update

Current state:

- `init --merge` skips LLM synthesis to preserve hand-written content.
- `update` still can synthesize the full updated document when a provider key is present.
- That means manual notes outside managed markers may be rewritten by the LLM.

Why this matters:

The safety promise is that update preserves manual content. If LLM mode rewrites the whole document, the promise becomes conditional.

Lean fix:

- Default `update` to static managed-section replacement.
- If LLM synthesis is used in update, run it only on managed section bodies, not the entire file.
- Simpler option: always skip LLM synthesis during `update` and print a note.

Acceptance test:

- A hand-written paragraph outside managed markers remains byte-for-byte unchanged after `agents-md update` with provider env vars set.

Do not build:

- Do not add a rich merge engine.
- Do not ask the LLM to "respect" manual notes and hope.

### 4. Score dry-run output

Current state:

- `init --dry-run` says quality is "not scored in dry-run" because the file is not written.

Why this matters:

Dry-run is the safest first interaction. It should show the score before the user writes anything.

Lean fix:

- Refactor `lint_file` into `lint_text(text, root=None)` plus the existing file wrapper.
- Score the generated content in memory during dry-run.

Acceptance test:

- `agents-md init --no-llm --dry-run` prints a quality score.
- Existing `agents-md lint` behavior is unchanged.

Do not build:

- Do not write a temp AGENTS.md to score it.
- Do not create a separate scoring path with duplicated rules.

### 5. Make provider defaults less stale-prone

Current state:

- Provider default models are hardcoded.
- Model availability changes over time.

Why this matters:

The project is mostly static and offline, which is good. But LLM synthesis will look broken if default model names go stale.

Lean fix:

- Keep static defaults, but add provider-specific error messages that explain how to pass `--model`.
- Add a tiny test ensuring defaults are only used when provider synthesis is requested.
- Document that `--no-llm` is the stable path.

Do not build:

- Do not call provider APIs just to discover models.
- Do not add network checks to normal CLI startup.
- Do not add a provider abstraction package.

## Best next product bets

These are the ideas most likely to make the project meaningfully better.

### A. Add a small fixture corpus and golden-output tests

Problem:

The current tests are good unit tests, but they do not prove the generator feels smart across real repo shapes.

Lean approach:

- Add `tests/fixtures/repos/` with tiny synthetic repos:
  - Python library with pytest and no entry point
  - Python CLI with uv and project scripts
  - FastAPI app with `uvicorn` or `fastapi dev` hints
  - Next.js TypeScript app with app router, aliases, Vitest
  - pnpm workspace with two packages
  - Go module with `cmd/`
  - Rust workspace with `cargo nextest` absent and normal cargo present
  - repo with README duplication
  - repo with `.env.example`
  - repo with migration command
- Store expected AGENTS.md snippets, not full snapshots.
- Test properties:
  - no `agents-md` self-reference leaks
  - no generic style rules
  - exact command count is stable
  - output is under a line threshold
  - risky commands appear in Ask First
  - docs duplication is removed

Why it is lean:

Fixtures make every future detector safer without adding runtime behavior.

Do not build:

- Do not clone large public repos into tests.
- Do not snapshot entire generated files unless output churn is intentionally controlled.

### B. Add `agents-md explain`

Problem:

The tool removes facts via deduplication, but users need to trust why something was kept or removed.

Current behavior:

- `--verbose` prints scanner and dedup diagnostics to stderr.

Lean approach:

Add:

```bash
agents-md explain
agents-md explain --json
```

It should show:

- docs read
- facts detected from manifests
- lines kept
- lines removed and why
- generated sections with source files
- warnings about uncertain or missing commands

Why it is useful:

It makes the core thesis inspectable. Users can see that the tool is not just templating.

Do not build:

- Do not add an interactive UI.
- Do not add a web report.
- Do not dump every normalized README fact by default.

Minimal output shape:

```text
Docs read:
- README.md

Kept:
- test: `python -m pytest` from pyproject.toml

Removed:
- install: `pnpm install` because README.md already says it

Warnings:
- No run command detected. Add one manually if this repo has a local app entry point.
```

### C. Add a local "first-run value" benchmark

Problem:

The README borrows credibility from the ETH study. The project needs its own honest proof, even if modest.

Lean approach:

Create a script or docs page that runs `agents-md init --no-llm --dry-run` across a small fixture corpus and reports:

- output line count
- quality score
- dedup removed count
- exact command count
- empty convention rate
- warnings

This is not a claim that agents solve tasks better. It is a product health benchmark.

Later, add optional agent-task evals only if there is a clean, reproducible harness.

Do not build:

- Do not claim performance improvements without real agent-task evidence.
- Do not make benchmarks require API keys.
- Do not add paid evals to CI.

### D. Improve high-signal detectors slowly

Principle:

One good detector beats ten noisy detectors.

Detector acceptance rules:

- The fact must be hard for an agent to infer quickly.
- The detector must have a clear source file.
- False positives must be rare.
- Output must fit in one line.
- There must be tests for positive and negative cases.
- The detector must not add a dependency.

Good detector candidates:

#### Python

- `manage.py` plus Django dependency:
  - command: `python manage.py test`
  - risky: migrations via `python manage.py migrate`
- FastAPI entry point:
  - only if `main.py`, `app.py`, or package module has a clear `app = FastAPI()`
  - command candidate: `uvicorn module:app --reload`
  - keep as warning if uncertain
- Alembic:
  - boundaries: ask before `alembic upgrade head`
  - conventions: migrations live in `alembic/versions`
- Nox/tox:
  - commands: `nox`, `tox`
  - single test still from pytest if visible
- `pytest.mark` custom markers:
  - convention only if markers are registered in config

#### JavaScript and TypeScript

- Playwright:
  - command: `pnpm playwright test` or package script if present
  - boundary: ask before updating snapshots unless script name implies snapshot update
- Next.js app router:
  - convention: route files live under `app/`
  - avoid explaining Next.js itself
- Workspace packages:
  - command: package-filtered test/build if lockfile and workspace config make it obvious
  - avoid generating child files automatically
- ESM vs CJS:
  - detect `"type": "module"` and do not overstate beyond import style
- Path aliases:
  - already detected; add negative tests for aliases that do not point under `src/`

#### Go

- `cmd/<name>/main.go`:
  - run command: `go run ./cmd/<name>`
- `go.work`:
  - stack: Go workspace
  - testing: still `go test ./...`
- `internal/`:
  - convention: internal packages are not importable outside parent tree

#### Rust

- Cargo workspace:
  - stack: Rust workspace
  - command: `cargo test --workspace`
- `cargo-nextest`:
  - only if config or scripts indicate it
- `clippy`/`fmt`:
  - command only if Makefile/CI uses it, or maybe in lint section if project config exists

#### CI

- Read GitHub Actions jobs for exact commands.
- Use CI commands as stronger evidence than guessed defaults.
- If CI has matrix commands, keep only the narrowest useful local command.

Do not build:

- Do not parse every language AST deeply.
- Do not infer commands from README prose if a manifest gives a better source.
- Do not emit framework tutorials.

### E. Add "warnings" as a first-class scan output

Problem:

Some missing facts are more useful as warnings than generated instructions.

Examples:

- "No single-test command detected."
- "Package manager not detected from a lockfile."
- "Multiple JS package managers found."
- "README duplicates most generated commands."
- "AGENTS.md is over 150 lines."
- "Existing AGENTS.md has manual content and managed sections."

Lean approach:

- Add `warnings: list[ScanWarning]` to `ScanResult`.
- Print warnings in `--verbose`, `explain`, and maybe summary.
- Do not add a "Warnings" section to generated AGENTS.md by default.

Why:

Warnings help the human improve the repo without making the agent read more text forever.

### F. Make the quality score less arbitrary over time

Current state:

The score is useful as a heuristic but not calibrated against real outcomes.

Lean approach:

- Keep the score simple.
- Add `agents-md lint --explain-score` or enrich JSON output.
- Add score tests for known bad/good examples.
- Track false positives in issues.
- Consider separate "risk flags" from numeric score:
  - too long
  - README duplicate
  - no exact commands
  - no boundaries
  - generic style rules

Do not build:

- Do not pretend 85/100 mathematically means performance improves.
- Do not add a complicated scoring model.
- Do not tune weights without examples.

### G. Support path-scoped instructions only as an explicit plan

Problem:

Codex supports nested instruction files and overrides. Monorepos may need local instructions. But auto-writing many files can create context sprawl.

Lean approach:

Add a planning command before generation:

```bash
agents-md split-plan
```

It should output:

- detected package/workspace boundaries
- whether root AGENTS.md is likely enough
- proposed child files only when there is a strong reason
- estimated loaded context if Codex starts in each path

Make writes explicit:

```bash
agents-md split-plan --write
```

Acceptance criteria:

- For small repos, it says "do not split."
- For monorepos, it proposes at most one child file per package boundary.
- It never creates files in vendor, build, dist, node_modules, or generated dirs.

Do not build:

- Do not auto-spray AGENTS.md files across every folder.
- Do not create a `.agents/` memory system.
- Do not make split files the default v0 behavior.

### H. Add copy-pasteable issue templates for detector misses

Problem:

The best detector ideas will come from users running it on real repos and saying "it missed X" or "it lied about Y."

Lean approach:

Add issue templates:

- "missed convention"
- "wrong command"
- "false positive"
- "docs duplication"

Each asks for:

- package manager
- relevant manifest snippet
- generated line
- expected line
- whether README already mentions it

Why:

This grows the tool from real failures, not imagination.

### I. Add `--fail-on-placeholder`

Problem:

Generated lines like "add the exact command after..." are honest, but CI users may want to fail if the file contains placeholders.

Lean approach:

Add to lint:

```bash
agents-md lint --check --fail-on-placeholder
```

Placeholder examples:

- "No high-confidence..."
- "add the exact command..."
- `<path>`
- `<name>`
- `test_example.py::test_name`

Why:

It lets serious repos enforce a fully actionable AGENTS.md without changing default behavior for new repos.

Do not build:

- Do not remove placeholders entirely. New repos benefit from honest gaps.

### J. Add `--max-lines` and `--max-bytes`

Problem:

Codex has a default project-doc byte cap. Line count is helpful, but bytes are the actual prompt input concern.

Lean approach:

```bash
agents-md lint --max-lines 120 --max-bytes 12000
```

Default remains current scoring. Extra thresholds are optional for strict teams.

Do not build:

- Do not enforce tiny defaults that punish legitimate repos.
- Do not hide useful content to satisfy a byte target.

## Ideas that sound good but should not be built now

### 1. A web dashboard

Reason to avoid:

It creates hosting, UI, auth, analytics, and maintenance burden. The product is a CLI for a file.

Better:

Make `--json` and `explain --json` good enough for others to build dashboards.

### 2. Mandatory LLM generation

Reason to avoid:

The core differentiator is useful static output without an API key. LLM mode should polish, not define the product.

Better:

Keep LLM optional and make static mode excellent.

### 3. Multi-format output for every agent

Reason to avoid:

`CLAUDE.md`, `.cursorrules`, Copilot instructions, Gemini files, and config sync quickly become a drift-management product.

Better:

Keep `AGENTS.md` as canonical and maintain the `CLAUDE.md` symlink behavior. Revisit only if users ask repeatedly.

### 4. A `.agents/` memory system

Reason to avoid:

That is a different product: persistent project memory. It may be useful, but it contradicts the "short over padded" thesis unless handled with extreme care.

Better:

Support path-scoped AGENTS only after `split-plan` proves need.

### 5. Deep AST architecture summaries

Reason to avoid:

Agents can read code. Architecture summaries go stale and encourage broad exploration.

Better:

Detect only conventions that change behavior: error flow, import boundaries, risky commands, generated dirs, test helpers.

### 6. Telemetry

Reason to avoid:

Trust matters. A tool that scans repositories should not phone home by default.

Better:

No telemetry. Encourage users to paste `agents-md explain --json` into issues when they want help.

### 7. Automatic PR comments

Reason to avoid:

This adds CI token permissions and noise.

Better:

Keep the GitHub Action as a pass/fail lint step with JSON output available.

### 8. Model/provider auto-discovery

Reason to avoid:

It adds network calls, provider variance, and stale API coupling.

Better:

Let users pass `--model`. Keep defaults documented and tested at the import/error-message level.

## Better README claims to avoid overpromising

Keep:

- "Generate short, useful AGENTS.md files."
- "Reads README/docs before writing."
- "Zero runtime dependencies."
- "Works offline."
- "Lint any AGENTS.md."

Avoid:

- "Improves agent performance" as a guaranteed claim.
- "Proven to help."
- "Understands your codebase."
- "Best AGENTS.md generator."
- "Benchmark-backed" until a real benchmark exists.

Better phrasing:

- "Designed around the failure mode reported by the ETH AGENTS.md study."
- "Optimizes for minimal, repo-specific instructions."
- "Makes generated context inspectable and update-safe."

## Implementation guardrails

### Keep scanner growth controlled

`scanner.py` is already the largest file at more than 700 lines. It is still understandable because it is one cohesive static scanner, but future detectors can make it messy.

Split only when there is a real boundary:

- `scan_js.py`
- `scan_python.py`
- `scan_go.py`
- `scan_rust.py`
- `scan_tasks.py`

Do not split only to satisfy line counts. Split when tests and review become harder because unrelated language logic sits together.

### No runtime dependencies by default

This is one of the strongest product advantages. Preserve it.

Allowed:

- Python standard library
- optional provider SDK extras
- dev dependencies for tests/build

Not allowed without a very strong reason:

- rich terminal UI libraries
- parser frameworks
- LLM orchestration libraries
- GitHub API clients
- telemetry packages

### Prefer small public APIs

The package is mostly a CLI. Keep internal Python APIs private unless users ask for library use.

If adding library support later, expose only:

- `scan_repo`
- `render_document`
- `lint_file` / `lint_text`

Do not expose every helper.

### Every detector needs negative tests

False positives are worse than missing a line because they put wrong instructions into every future agent session.

Minimum tests for any detector:

- detects the intended repo shape
- ignores a similar but wrong repo shape
- does not scan skipped dirs
- produces one concise line
- includes the source path

## Second-pass source-backed analysis

This section records what the current external landscape implies for `agents-md`.

### Official guidance implications

#### Codex instruction loading favors byte discipline

OpenAI's Codex docs say Codex builds an instruction chain from global and project files, walks from the project root to the current directory, and stops adding files once the combined project-doc size reaches `project_doc_max_bytes`, defaulting to 32 KiB.

Implications:

- `agents-md lint` should eventually score bytes, not only lines.
- Generated root files should stay short because nested instructions may be appended later.
- A future `split-plan` should estimate total loaded bytes for likely working directories.
- Long generated "architecture overview" sections are especially risky because they consume the always-loaded root budget.

Source: https://developers.openai.com/codex/guides/agents-md

#### GitHub Actions reproducibility favors pinning

GitHub's secure-use docs say a compromised action can access repository secrets and `GITHUB_TOKEN`, and that pinning actions to a full-length commit SHA is the immutable-release option. Tags are convenient but can move.

Implications:

- The README can show a tag for usability, but the docs should mention SHA pinning for security-sensitive workflows.
- The composite action should not install an unpinned PyPI package by default.
- Release notes should include the exact action tag and package version together.
- A future `SECURITY.md` should describe how users should pin the action.

Source: https://docs.github.com/en/actions/reference/security/secure-use

#### OpenSSF Scorecard points to low-cost trust work

OpenSSF Scorecard checks include `Pinned-Dependencies`, `Security-Policy`, `Token-Permissions`, `CI-Tests`, `Packaging`, and related supply-chain signals.

Implications:

- Add `SECURITY.md` before the project is widely shared.
- Keep workflow permissions minimal. The current publish workflow correctly scopes `contents: read` and `id-token: write` only in the publish job.
- Consider a Scorecard workflow later, but do not add a noisy badge until it is useful.
- Do not add unnecessary dependencies because every dependency creates another maintenance and security surface.

Source: https://github.com/ossf/scorecard

#### AGENTS.md is intentionally simple

The open AGENTS.md repository describes the format as a simple, open format and a README for agents.

Implications:

- `agents-md` should not add frontmatter, private metadata blocks, or custom schema requirements to the generated user-facing file.
- Managed markers and fingerprint comments are acceptable because they are hidden implementation metadata and keep updates safe.
- Human readability should remain a release gate.

Source: https://github.com/agentsmd/agents.md

### Research implications

#### ETH evaluation supports "minimal requirements"

The ETH AGENTS.md evaluation says context files can reduce task success and increase inference cost, and concludes context files should describe only minimal requirements.

Implications:

- "Generate less" is not just branding; it is the product safety model.
- Quality scoring should penalize generic requirements, not reward exhaustive coverage.
- Benchmarks should include "no context" as a baseline when actual agent-task evals arrive.
- The README should stay cautious and avoid guaranteed performance claims.

Source: https://arxiv.org/abs/2602.11988

#### Configuration study supports AGENTS.md as a natural starting point

The "Configuring Agentic AI Coding Tools" study found repository-level context files dominate configuration mechanisms, with AGENTS.md emerging as an interoperable standard across tools. It also found advanced mechanisms such as Skills and Subagents are less common.

Implications:

- Root `AGENTS.md` is the right initial target.
- Advanced mechanisms should be optional and late.
- The CLI should remain useful to teams that do not use any particular agent framework.
- Compatibility matters more than novelty.

Source: https://arxiv.org/abs/2602.14690

#### Codified Context is relevant but not the v0 target

The Codified Context paper describes a large 108,000-line system using a hot-memory constitution, 19 specialized agents, and 34 on-demand spec documents.

Implications:

- Path-scoped or tiered context can matter for large systems.
- `agents-md` should not default to that model for small repos.
- `split-plan` should be advisory first, write later, and only when repo shape justifies it.
- A 30-line root file plus optional package-local files is preferable to one large generated root manifesto.

Source: https://arxiv.org/abs/2602.20478

## Adjacent tool positioning

This is not a dunk list. These tools show real demand. The point is to understand where `agents-md` should stay different.

### `agentmd-gen`

Observed positioning:

- Generates multiple context-file formats such as `CLAUDE.md`, `AGENTS.md`, `.cursorrules`, and Copilot instruction files.
- Has scoring and an `eval` command.
- Has tiered mode that writes a top-level file plus per-subsystem files under `.agents/`.

What to learn:

- Users want measurement, not only generation.
- Tiered context is a serious pattern for large repos.
- Multi-format output is attractive for teams using several agents.

What not to copy now:

- Do not make multi-format output the default.
- Do not write `.agents/` directories by default.
- Do not claim performance impact without reproducible local evidence.

Lean response:

- Build `explain` and fixture benchmarks first.
- Add `split-plan` before any tiered writes.
- Keep `AGENTS.md` canonical and `CLAUDE.md` as a symlink.

Source: https://pypi.org/project/agentmd-gen/

### `agents.ge`

Observed positioning:

- Treats `AGENTS.md` and tool-specific files as entrypoints.
- Uses `.agents/` as a durable source of truth for project memory, reusable rules, structured knowledge, and MCP definitions.
- Targets mixed-agent teams.

What to learn:

- There is market pull for project memory and cross-agent synchronization.
- Durable memory is a different product category than generating one lean file.

What not to copy now:

- Do not turn `agents-md` into a memory product.
- Do not add MCP sync.
- Do not add capture hooks.

Lean response:

- Mention memory tools as adjacent, not competing head-on.
- Preserve zero telemetry and zero runtime dependencies.
- If memory ever matters, integrate by reading explicit docs, not by owning the memory layer.

Source: https://agents.ge/

### `agentmd`

Observed positioning:

- Defines a separate `AGENT.md` with schema/frontmatter.
- Can generate Cursor, Claude, and Copilot files from one structured source.
- Explicitly contrasts AGENT.md with plain, free-form AGENTS.md.

What to learn:

- Some teams want schemas and adapters.
- Plain AGENTS.md remains valuable because it is consumed directly.

What not to copy now:

- Do not add frontmatter to generated AGENTS.md.
- Do not create a new schema unless the plain format cannot represent what users need.
- Do not create adapter churn before the core generator is trusted.

Lean response:

- Keep generated AGENTS.md simple.
- Make `lint --json` stable enough for external tools.
- If schema becomes necessary, apply it to machine output, not to the human-facing AGENTS.md.

Source: https://pypi.org/project/agentmd/

### `agentskill` / `agsk`

Observed positioning:

- Describes itself as forensic extraction.
- Analyzes directory tree, config, git history, import graph, symbols, tests, and style measurements.
- Supports many languages and can generate AGENTS.md.

What to learn:

- Rich static analysis can produce impressive repo-specific context.
- Fixtures and examples across languages are valuable credibility assets.

What not to copy now:

- Do not analyze commit history.
- Do not measure indentation, blank lines, and style distributions for AGENTS.md output.
- Do not add import graph analysis unless a specific generated line needs it.

Lean response:

- Use a narrow detector bar: only facts that prevent agent mistakes.
- Add more languages slowly through fixtures.
- Keep "style belongs to linters" as a hard rule.

Source: https://pypi.org/project/agsk/

## Competitive wedge

`agents-md` should not compete on "most complete project understanding." That path leads to bigger output, heavier scans, and fragile claims.

It should compete on:

1. Shortest useful AGENTS.md.
2. Best deduplication against existing docs.
3. Safest update semantics.
4. Most honest scoring.
5. Best first-run offline experience.
6. Clear source tracing for every generated line.
7. Low dependency and security footprint.

The tagline in product decisions should be:

> Generate less. Preserve more. Explain every line.

## Decision framework for new ideas

Before adding any feature, answer these questions:

1. Does this reduce repeated agent mistakes, or only make the tool feel smarter?
2. Does this write more text into always-loaded context?
3. Can the agent already discover this from README, manifests, or source in under one minute?
4. What is the false-positive cost if this detector is wrong?
5. Is the output one concise line?
6. Does this require a runtime dependency?
7. Does this create external state, network calls, telemetry, or credentials?
8. Can it be tested with one positive fixture and one negative fixture?
9. Does it preserve hand-written AGENTS.md content?
10. Would a maintainer understand why the line appeared?

If the answer to 2, 4, 6, or 7 is "yes" and the benefit is not obvious, do not build it.

## Implementation-ready cards

### Card 1: Pin package version in the GitHub Action

User story:

As a repo maintainer pinning `osmaneb23/agents-md/.github/actions/agents-md-lint@v0.1.1`, I want the action to install the matching `agent-context-md` package version so old workflows do not silently receive new lint behavior.

Files:

- `.github/actions/agents-md-lint/action.yml`
- `README.md`
- `tests/` only if adding a static action metadata test

Implementation:

- Add input `version` with default `"0.1.1"` for the current release line.
- Change install command to `python -m pip install "agent-context-md==${{ inputs.version }}"`.
- README example can show the default and mention users can override it.

Acceptance:

- Action metadata contains the version input.
- Install line is pinned.
- README no longer implies tag pinning alone pins package behavior.

Risk:

- Users on `@main` may get a default version older than latest until release metadata is updated.

Mitigation:

- In unreleased `main`, default to current package version and update it during release prep.

### Card 2: Update must never rewrite manual content

User story:

As a maintainer with manual notes above or below managed sections, I want `agents-md update` to preserve those notes byte-for-byte even if LLM provider keys are present.

Files:

- `src/agents_md/cli.py`
- `tests/test_cli.py`

Implementation:

- When `cmd_update` is called, skip LLM synthesis entirely by default.
- Print `LLM synthesis skipped in update mode to preserve manual content.` when provider keys are present and `--no-llm` was not passed.
- Optionally add a future explicit `--llm-managed-only`, but do not build it now.

Acceptance:

- Test creates AGENTS.md with manual text outside markers, sets `ANTHROPIC_API_KEY`, runs update, and asserts manual text is byte-identical.
- Existing update static behavior still passes.

Risk:

- Users expecting LLM polish during update lose that behavior.

Mitigation:

- Safety beats polish. Mention `init` can still use synthesis on new generated files.

### Card 3: Fingerprint docs and env examples

User story:

As a maintainer relying on `agents-md diff`, I want it to detect when README, docs, or env examples changed enough that generated output may be stale.

Files:

- `src/agents_md/fingerprint.py`
- `src/agents_md/dedup.py` if sharing doc discovery
- `tests/test_cli.py` or `tests/test_scanner_generator.py`

Implementation:

- Add root Markdown docs except output file and symlink aliases.
- Add `docs/**/*.md`.
- Add `.env.example`, `.env.sample`, `example.env`.
- Keep stable sorted ordering.

Acceptance:

- Changing README makes `diff` report changed README.
- Changing `.env.example` makes `diff` report changed env example.
- `CLAUDE.md` symlink to `AGENTS.md` is still excluded.

Risk:

- More frequent diff notices.

Mitigation:

- That is correct if docs affect deduplication.

### Card 4: Score dry-run output

User story:

As a first-time user, I want `agents-md init --dry-run` to show quality score before writing a file.

Files:

- `src/agents_md/quality.py`
- `src/agents_md/cli.py`
- `tests/test_quality.py`
- `tests/test_cli.py`

Implementation:

- Add `lint_text(text, root=None)`.
- Make `lint_file` call `lint_text`.
- In dry-run summary, score `content` in memory.

Acceptance:

- Dry-run summary prints `quality <score>/100`.
- `lint_file` remains compatible.
- README duplication scoring works when a root path is passed.

Risk:

- `lint_text` needs root context for README duplication.

Mitigation:

- Accept optional root; if absent, skip README duplication and say so in docs only if exposed publicly.

### Card 5: Add warnings without adding a generated section

User story:

As a user, I want the CLI to tell me when it is uncertain without forcing that uncertainty into AGENTS.md.

Files:

- `src/agents_md/types.py`
- `src/agents_md/scanner.py`
- `src/agents_md/cli.py`
- tests

Implementation:

- Add `ScanWarning(code, message, source=None)`.
- Populate warnings for no package manager, no single test, multiple package managers, placeholders, no commands.
- Print in `--verbose` and later `explain`.

Acceptance:

- Warning appears in verbose output.
- Generated AGENTS.md remains unchanged.

Risk:

- Too many warnings feel noisy.

Mitigation:

- Keep warning set small and actionable.

### Card 6: Add explain before adding more detectors

User story:

As a skeptical maintainer, I want to see why `agents-md` kept or removed each important line.

Files:

- `src/agents_md/cli.py`
- `src/agents_md/types.py`
- `src/agents_md/dedup.py`
- tests

Implementation:

- Add subcommand `explain`.
- Reuse scan and render paths.
- Human output by default, JSON with `--json`.
- Include docs read, detected commands, detected conventions, dedup removed lines, and warnings.

Acceptance:

- `agents-md explain --json` returns stable JSON.
- No generated files are written.
- Does not require an LLM key.

Risk:

- Explain becomes a second implementation of generation.

Mitigation:

- It must call the same scan/render code as `init`.

### Card 7: Fixture corpus

User story:

As a contributor adding a detector, I want small fixture repos that show expected behavior and prevent regressions.

Files:

- `tests/fixtures/repos/...`
- `tests/test_fixtures.py`

Implementation:

- Use tiny text fixtures only.
- Assert snippets/properties, not full snapshots.
- Include negative cases.

Acceptance:

- Fixtures cover Python CLI, Python library, JS app, monorepo, Go, Rust, env example, migration, README duplication.
- Full test suite stays under one second locally if possible.

Risk:

- Fixture sprawl.

Mitigation:

- One fixture per behavior class, not per framework version.

## Public credibility checklist

These are not product features, but they make the project look safer and easier to adopt.

### Add `SECURITY.md`

Keep it short:

- supported versions
- how to report vulnerabilities
- do not include secrets in reports
- note that the tool scans local files and has no telemetry

Why:

Open-source users look for a vulnerability reporting path. OpenSSF Scorecard also recognizes a security policy.

### Add focused issue templates

Templates:

- wrong generated command
- false-positive convention
- missing convention
- docs dedup issue

Why:

Bad detector reports need structured data. Otherwise issues become "it was bad on my repo" with no reproduction.

### Add `examples/` only if generated from fixtures

Good:

- `examples/python-cli.AGENTS.md`
- `examples/next-app.AGENTS.md`
- `examples/go-module.AGENTS.md`

Bad:

- broad tutorial examples
- fake impressive output not tied to fixtures

Rule:

Examples should be generated by tests or a script, not hand-curated marketing copy.

### Add a release checklist

Short file or docs section:

- bump `pyproject.toml`
- bump `__version__`
- bump action default package version
- regenerate AGENTS.md
- run tests
- build
- twine check
- publish release
- verify PyPI install

Why:

This prevents the exact kind of action/package/version mismatch that already almost happened.

### Consider dependency update automation later

This project has almost no dependencies, which is good. If optional SDKs need maintenance, Dependabot or Renovate can open PRs.

Do not add it until there is real dependency churn.

## Anti-bloat release gates

Before any release, ask:

1. Did generated AGENTS.md for this repo stay under 80 lines?
2. Did runtime dependencies stay at zero?
3. Did the README avoid stronger claims than the evidence supports?
4. Did every new detector include a negative test?
5. Did update preserve manual content?
6. Did `--no-llm` remain a first-class path?
7. Did the action and package versions stay aligned?
8. Did CI stay fast?
9. Did the release avoid new external services?
10. Did the change make the file shorter, safer, more trusted, or more measurable?

If not, slow down.

## My honest answer to "is this useful?"

Yes, but only if it stays disciplined.

The useful part is not "AI generates a markdown file." That is common and often bad.

The useful part is:

- deduplication against existing docs
- exact commands
- small output
- explicit safety boundaries
- safe managed updates
- linting any AGENTS.md, including hand-written ones

The project becomes useless if it turns into:

- another huge context generator
- a memory framework
- a multi-agent scaffold
- an architecture summarizer
- an LLM-first wrapper with heavy dependencies

The lean wedge is strong: "generate less, verify more."
